# 03: Database Migration Strategy

This document outlines the strategy and process for managing database schema changes using Entity Framework Core Migrations across the NovaCommerce microservices.

## Overview

Each microservice (`inventory`, `sales`, `identity`) maintains its own isolated database schema. Database migrations are managed independently for each service using Entity Framework Core's migration tools. This approach ensures that schema changes are version-controlled, repeatable, and aligned with the lifecycle of each microservice.

## Generating Migrations

To generate a new migration for a specific service (e.g., `inventory`), navigate to the `src` directory of that service in your terminal and execute the following command:

```bash
dotnet ef migrations add [MigrationName] -o Data/Migrations
```

-   Replace `[MigrationName]` with a descriptive name for your migration (e.g., `AddProductImageField`).
-   The `-o Data/Migrations` flag specifies that the migration files should be placed in a `Data/Migrations` subdirectory within the `src` folder, maintaining a consistent project structure.

This command will create new migration files that capture the changes made to the `DbContext` and its associated entities since the last migration.

## Applying Migrations

Database migrations can be applied in several ways, depending on the environment and deployment strategy:

### 1. During Development (Local Database)

To apply all pending migrations to your local development database, navigate to the `src` directory of the respective service and run:

```bash
dotnet ef database update
```

This command will create the database if it doesn't exist and apply all pending migrations.

### 2. Programmatically (During Application Startup)

For automated deployments, especially in containerized environments like Kubernetes, migrations can be applied programmatically during application startup. This is typically done in the `Program.cs` or `Startup.cs` file of the service.

Example (in `Program.cs` or `Startup.cs`):

```csharp
public static IHost MigrateDatabase<TDbContext>(this IHost host) where TDbContext : DbContext
{
    using (var scope = host.Services.CreateScope())
    {
        var services = scope.ServiceProvider;
        try
        {
            var dbContext = services.GetRequiredService<TDbContext>();
            dbContext.Database.Migrate();
        }
        catch (Exception ex)
        {
            // Log errors
            var logger = services.GetRequiredService<ILogger<Program>>();
            logger.LogError(ex, "An error occurred while migrating the database.");
        }
    }
    return host;
}

// In Main method:
// CreateHostBuilder(args).Build().MigrateDatabase<InventoryDbContext>().Run();
```

**Note**: While convenient, applying migrations at startup should be carefully considered for production environments, especially in high-availability scenarios, as it can introduce downtime if migrations are long-running or involve schema locks. A dedicated migration job or tool is often preferred for production.

### 3. Using `dotnet ef database update` in CI/CD

In CI/CD pipelines, a dedicated step can execute `dotnet ef database update` against the target database after deployment. This ensures that the database schema is always up-to-date with the deployed application version.

## Best Practices

*   **Small, Incremental Migrations**: Keep migrations small and focused on a single logical change.
*   **Review Generated Migrations**: Always review the C# code generated by `dotnet ef migrations add` before committing.
*   **Idempotency**: Ensure migrations are idempotent, meaning they can be run multiple times without causing errors. EF Core migrations are designed to be idempotent.
*   **Backup Before Production Migrations**: Always back up your production database before applying migrations.
*   **Rollback Strategy**: Have a clear rollback strategy in case a migration introduces issues.
